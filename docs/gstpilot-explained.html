1 · What it is, and the rules it can't break

GSTPilot answers questions like “footwear ka GST rate kya hai?” or “Amazon pe bechta hu, TCS kitna katega?” — in the seller's own Hinglish — and backs every legal claim with the exact section or notification it came from. When the law it holds doesn't cover a question, it says so instead of guessing. When a question smells like a live dispute (a notice, a penalty, a seizure), it stops and points to a Chartered Accountant.

Six promises are non-negotiable — they're the product's constitution, enforced in code, not vibes:

PromiseWhy it matters
Every legal claim cites a retrieved chunkA tax answer you can't verify is worse than no answer. A deterministic gate checks this — you can't sweet-talk it.
False-answer ≈ 0 on “unanswerable” questionsConfidently answering law we don't have is the catastrophic failure. Better to abstain.
Disputes always escalate (T3 recall = 1.0)A live proceeding needs a professional, not a chatbot.
Rates / dates / thresholds come from documents or code — never model memoryModels misremember numbers just often enough to be dangerous.
Law text is never hand-editedThe corpus is an audit trail; every doc has a source + as-on date + checksum.
Identity fields are never filled by a modelA chunk's id, a case's labels — anything that gates correctness — is human/deterministic only.

2 · The one big idea: two separate paths

The whole architecture fits in a sentence: a user's question never touches a PDF.

Offline (runs when the law changes)

Government PDFs → cleaned text → cut into “chunks” of law → turned into numbers (embeddings) → stored in the database. Slow, careful, run rarely.

Online (runs on every question)

Question → search the database → write a cited answer → check it → reply. Fast, and auditable, because it only ever reads what's already been vetted.

410 gov PDFs→ extract (Python)pdfplumber→ chunkers (TS)split at legal lines→ embeddingsbge-m3, local→ Supabase1,064 chunks: text + search + vector

This split is what makes answers fast and trustworthy: the expensive, error-prone work (reading 200-page PDFs) happens once, offline; the live path only queries clean, checksummed data.

3 · Offline: turning the law into a database

Getting the law onto disk

The corpus is two layers: base (the consolidated CGST Act, IGST Act, CGST Rules — 3 big PDFs) and stream (407 notifications & circulars pulled from the government's JSON API). Every file is recorded with its source, an “as-on” date, and a SHA-256 checksum — because “the law” is really “a specific version of a document,” and government pages rot.

code scripts/download-stream.ts corpus/manifest.json

Reading the PDFs (no OCR)

A small Python script opens each PDF with pdfplumber, which reads the text layer the PDF already contains (these are digital documents, not scans — so no OCR is used). It de-noises: strips invisible characters, fixes hyphenated line breaks, drops repeating page headers/footers.

codescripts/extract/extract.py

Cutting it into chunks — at legal boundaries, not word counts

A chunk is one complete legal thought: a whole section or rule, with its provisos (“Provided that…”), explanations and exceptions glued on. Split a rule from its exception and retrieval will happily serve confident, cited, incomplete law — the worst kind. The boundary detectors are deliberately paranoid because legal text is full of lines that start with “N.” but aren't sections (footnotes, numbered Explanations).

// a real rule heading always carries ".-" shortly after its number; a footnote doesn't
sectionRe: /^(?:\d{0,2}\s*\[\s*)?(\d{1,3}[A-Z]{0,2})\.?\s*\[?\s*(?=[A-Z]).{0,260}?[.:]\s*-/

Each chunk gets a deterministic id like CGST-ACT/s16 or CGST-RULES/r89 — identical on every run, so amendments can address it and tests can assert on it. Old/replaced provisions are kept but marked superseded (filtered out of search, preserved for the audit trail).

code lib/ingestion/chunk-acts.ts lib/ingestion/chunk-notifications.ts lib/ingestion/enrich.ts
The three-tier metadata rule. A chunk's facts come from three sources of different trust: config (things we know — which act), regex (structure the drafters wrote — section numbers), and model (judgment labels only, from a closed list). The model never fills an identity field, because deterministic sources fail loudly while models fail plausibly.

Turning text into numbers (embeddings)

An embedding is a list of 1,024 numbers that captures a text's meaning, so texts about the same idea land near each other even in different words. GSTPilot runs the open bge-m3 model locally (no API, no per-token cost) — it handles Hinglish queries against English law. The model is pinned: an embedding is only comparable to embeddings from the exact same model weights.

A fix from this week. Big chunks were being embedded on only their first 6,000 characters (an old memory-saving cap) — so Rule 89's refund formula, buried deeper in a 16k-char chunk, was invisible to search. We removed the cap and now embed giants whole (bge-m3 handles up to ~8,192 tokens), with a tripwire that flags any chunk too big even for that. See §6.

4 · The knowledge store

Everything lands in one Postgres table (via Supabase) — each chunk row holds its text, a full-text-search column, and a vector(1024) for meaning-search, side by side. One ordinary database does both jobs; no separate “vector database” needed (that's what the pgvector extension buys us).

5 · Online: the supervised agent team

A question passes down a line of small workers, each watched by a gate that can stop the line. Every step is logged so the whole trajectory is auditable.

INTAKEhaiku: intent + risk tier G1 · schemabad JSON → default to T3→ T3? → CA handoffnever reaches a model answer
T1/T2 → RETRIEVALhybrid search G2 · relevance floor→ RESOLUTIONsonnet + calculators G4 · citations ⊆ sources G3 · recompute numbers→ REPLYhaiku tone G5 · claim check→ you

The three tiers decide the path: T1 = how the law works in general · T2 = computes your money or a deadline · T3 = a notice / penalty / dispute → escalate. When intake is unsure, it fails up the ladder (worst case: a routine question meets a CA), never down.

5b · The third move (ASK) and the router Phase 8b

The line above had only two exits: a cited answer, or an abstention. A question that was answerable in principle but missing an input — a late fee with no dates — had nowhere to go but "the sources don't cover this". Phase 8b adds a third move: ASK, and splits the front of the line into a router that sends each question down the lane that fits it.

INTAKEnow also picks a LANE→ ROUTERreconcileLane→ rate-lookup calculation procedure (RAG) change-over-time escalate

Before a lane answers, it checks whether it has the inputs its tool needs — read straight from the tool's required-input schema. A missing input becomes one bundled friendly question ("which return — GSTR-3B, GSTR-1 or GSTR-9? the due date? nil return? turnover?"), carried across turns by the thread. Every tool you add teaches the ASK move for free, because the question is derived from the schema, never hand-written. The understanding step now also has a clock, so "5 days back", "aaj", "10 crore" resolve to real dates and numbers.

Rates as facts, not passages. A rate lives inside a giant schedule chunk where the item and its % often get split apart, so retrieval finds the item but not the number. Rates now come from a structured rate table and a lookup_rate step that returns the % pre-cited, exactly like the calculators. One move fixes three bugs at once: the buried-rate dilution, the citation-gate over-abstention (a pre-cited fact can't trip the gate), and the English-works / Hinglish-abstains inconsistency (lookup is language-agnostic — "chappal" resolves to footwear). Conditional items ask the price threshold ("₹2,500 se kam ya zyada?"). The table is model-compiled and still needs a human to verify it against the source PDFs.

The gate got gentler. It used to discard a whole answer over one untagged sentence — the reason nearly every RAG answer abstained. Now it drops just the offending sentence and keeps the cited remainder, abstaining fully only if nothing grounded survives. The hard bar stays: an invented citation is still never shown.

6 · Retrieval — and the fix from this week

First, transform the question

Before searching, one Haiku call rewrites the seller's words into the statute's vocabulary — “TCS kitna katega” → “electronic commerce operator collect tax at source” (the law never says “TCS”!). References like “section 52” skip search entirely and resolve straight to a chunk id, because similarity is the wrong tool for identity. And the meaning-channel embeds a short fake hypothetical answer, not the question — the corpus is full of answers, so an answer-shaped probe lands nearer the truth.

codelib/retrieval/transform.ts

Two channels, fused by rank

Search runs two ways with complementary blind spots: dense (meaning) finds “invoice mila par payment nahi kiya” ≈ Section 16 even with no shared words; keyword (exact tokens, with hand-built rarity weighting so “footwear” outweighs “rate”) finds codes like “GSTR-9C” that embeddings blur. They're fused by rank, never raw score (a cosine of 0.83 and a keyword score of 14.2 are apples and oranges).

Try the fusion math (RRF) — a chunk's rank in each channel (blank = not found):
dense rank   keyword rank  
score = 1/(60+dense) + 1/(60+keyword) · being solid in both beats spiking in one

This week's two fixes (the “refund” bug)

A live question — “how do i get gst refund” — was wrongly abstaining. Digging in found two structural causes, both now fixed:

  1. Giant chunks, embedded half-blind. The refund section (s54, 11.9k chars) and Rule 89 (16.3k chars) were embedded on only their first 6,000 chars. Fix: stop truncating — embed giants whole, one at a time to stay within memory, with a tripwire for anything over the model's real limit. Result: s54 jumped from search rank #15 to #2. scripts/embed-chunks.ts
  2. The statute lost to the notification “stream.” Broad “how do I…” questions pulled plain-language circulars above the actual Act. Fix: an intent-aware boost — for procedural questions, lift Act & Rules above notifications; for rate questions (where a notification genuinely is the law) leave it untouched. migrations/0009_doc_type_boost.sql
The honest twist. Retrieval got measurably better, but the answer still abstained — because the real bottleneck turned out to be the citation gate over-abstaining (see §14), not retrieval. Good example of “fix the thing the evidence points at, not the thing you assumed.”

7 · The five gates — the ladder rule

Catch each kind of failure on the cheapest rung that can see it.

GateChecksHow (and why it can't be gamed)
G1 schemaintake JSON is well-formeda zod parse — free; a double failure defaults to T3 (fail up)
G2 relevance floorthe best chunk isn't hopelessly unrelateda similarity threshold — if even the top chunk is weak, generation ran on sand
G4 citationsevery [tag] is a chunk we actually retrievedSet.has() — arithmetic, not a reader; an invented citation simply isn't in the set
G3 recomputeevery number matches its cited source / calculatorplain code re-derives the figure — the model can't fudge a date-diff
G5 claim checkthe friendly rewrite didn't quietly add or strengthen a claimthe only gate that spends a model call — because “this rephrase over-promises” needs a reader

Verification is easier than generation — that's why a model may check what a model wrote (G5), but only after the free arithmetic gates (G1–G4) have done their work. Every failure path ends the same safe way: one regeneration with the errors named (a targeted edit beats a blind retry), then abstention — never a silent bad answer.

// G4 — you cannot argue with set membership
const invalid = citedTags.filter(id => !providedSources.has(id));
// fail → regenerate with errors NAMED → still failing → abstain

8 · “Model proposes, code disposes”

Money math never happens in prose. The model extracts the parameters and calls a pure function; the figure comes back with its own legal citations attached.

gstrLateFee({ due_date:"2026-02-20", filing_date:"2026-03-01",
              nil_return:false, annual_turnover_inr:20_000_000 })
// → { days_late: 9, fee_per_day: 50, computed_fee: 450, payable: 450,
//     citation_ids: ["CGST-ACT/s47","NOTIF-CT/nt-2021-019", ...] }

Why: “due 20-Feb, filed 1-Mar — 9 or 10 days late?” A model guessing likely-looking digits gets such off-by-ones wrong just often enough to hurt; a date-diff in code is exact and testable. Interest under s50 (18% p.a.) works the same way.

9 · Permission to not know

Models hallucinate because training rewarded answering. GSTPilot makes abstention a first-class, instructed output — an exact phrase, framed as a success: “the available sources don't cover this point.” The gates complete the economics — a made-up claim costs a regeneration, while abstaining sails straight through. Honesty is made cheaper than bluffing. On the 20 deliberately-unanswerable test questions, it refuses all 20.

10 · Evals — the ruler, and why it wobbles

The measuring stick was built before the agent. 60 “golden” cases (40 answerable / 20 unanswerable, 7 T3), each with expected chunks, exact required facts, forbidden strings, intent and tier.

Per-metric, never blended. A single “quality score” of 0.7 could be great retrieval + broken escalation, or the reverse — the blend hides which layer broke. So each number grades one layer:

MetricGradesNowBar
recall@10retrieval0.775≥ 0.9
false-answer ratehonesty on unanswerable0= 0
T3 recallescalation safety1.0= 1.0
citation validityno invented citationsclean= 0 invalid
fact-matchanswer completeness~0.15, noisy≥ 0.8
Why the asterisk on fact-match. This week we found the number swings run-to-run (1/18 one run, 3/18 the next — on identical code), because a borderline answer flips between “answered” and “abstained.” You can't optimise against a jittery number, so the eval now runs each fact case a few times and reports the average pass-rate (EVAL_REPEAT), which is stable. To keep cost down it also runs a curated 30-case subset by default (EVAL_SAMPLE) that keeps every fact case.

11 · The self-improvement flywheel new this week

The system now learns from its own failures. A production failure becomes a test case; the test case gates every future change; the same failure can never silently return.

👎 in the app→ Triage queue/admin/triage→ Haiku pre-drafts labelsa speed-up, not the truth→ ⚠️ you approve every label→ Golden setversion bumps→ CI gates it forever

Why a golden set that never grows is a depreciating asset: the law gets amended, sellers phrase things in new ways, models get upgraded — a frozen test set quietly tests yesterday's product. Every real failure you capture permanently raises the floor.

⚠️ Your one rule here. Haiku pre-drafts the labels to save you typing, but you approve/correct every field — because these labels feed zero-tolerance gates. A wrong “expected fact” wouldn't just miss; it would teach CI to enforce a wrong answer forever. (The same three-tier rule: a model never fills a field that gates correctness.)

CI (GitHub Actions): every pull request runs a 25-case smoke test of the absolute gates (T3 recall, false-answer, citation validity) as a hard block — you can't merge a change that breaks them. The full suite runs nightly as a trend line.

14 · Where it stands, honestly — and what's next

Solid: the safety bars all hold — false-answer 0, T3 recall 1.0, citations always valid. And after Phase 8b the app works where it used to shrug: late fees, rates (incl. Hindi item words), registration, refunds, general math and change-over-time now answer, ask, or honestly abstain — instead of a blanket "sources don't cover this".

What Phase 8b changed: the biggest lever wasn't better retrieval — it was giving the agent a third move (ASK), turning facts (rates) into pre-cited lookups instead of prose to be fished out, and making the citation gate drop the bad sentence instead of the whole answer. Together those un-stuck the classes that were wrongly abstaining.

Honestly still open:

  1. The rate table is model-compiled and unverified — a wrong rate is exactly the "confident false answer" we forbid. It's cited + hedged + flagged verified:false, but it needs a human sitting with the source PDFs.
  2. Change-over-time is retrieval-bound — it narrates a real timeline only when ≥2 dated docs are actually surfaced; the full historical rate change still wants the "schedule-row summaries" ingestion lever.
  3. Evals are stale — we built and verified by running the app this session (by request). The golden set doesn't yet cover the new lanes; re-baselining is the honest next step before trusting numbers again.
