# GSTPilot — Code Walkthrough

> A plain-English, code-block-level guide to the whole codebase. Read this **beside the actual source** — it explains *what each block does and how*, not line-by-line syntax. For language keywords/operators (`async`, `?`, `override?`, `??`, `=>` …) see the companion **SYNTAX_GLOSSARY.docx**.

## The one-line mental model
A question enters the **API**, the **pipeline** classifies it and **routes** it to a **lane**; a lane either **looks up a pre-cited fact** / **runs a calculator**, **ASKS** for a missing input, or falls through to **retrieval + a grounded LLM answer** that must pass the **citation gates** — then streams back. Safety bars: every legal claim cites a source · disputes escalate to a human CA (tier T3) · never a confident false answer.

## Suggested reading order
1. **Entry & Orchestration** — how a request flows and who's in charge (`api/ask`, `pipeline`).
2. **Intake & Router** — how the question's type is decided.
3. **The ASK move & Tool Registry** — the "third move" and the schemas it reads.
4. **The Lanes** — the deterministic answer paths.
5. **Rates & Calculators** — the facts and math the lanes stand on.
6. **RAG & Retrieval** — the fallback path when there's no lane.
7. **The Gates** — the safety checks.
8. **Observability, Database & UI** — tracing, storage, and the chat screen.

If you read only three files: **`pipeline.ts`** (the spine), **`clarify.ts`** (the ASK move), **`verify-citations.ts`** (the safety).

## 1 · Entry & Orchestration

### `app/api/ask/route.ts`
This is the product's single HTTP endpoint: the browser POSTs a question here and gets a live-streaming answer back. It handles conversation memory (what the stateless model is allowed to "remember"), runs the pipeline, extracts citations, saves the turn, and streams every stage to the UI.

- **`dynamic = "force-dynamic"` / `maxDuration = 300`** — config constants that tell Next.js never to cache this route and to allow up to 300 seconds per request. *How*: streaming answers are unique per call and can run long (multiple model calls + gates), so caching is disabled and the serverless timeout is raised. Anand: so in case a response takes more than 300 seconds then on front end it will fail?
- **`VERBATIM_TURNS = 20`** — the memory window size. The last 20 messages are re-sent word-for-word; anything older is folded into a summary. This is the dividing line between "quote exactly" and "compress."
- **`buildContext(threadId)`** — assembles the text history the model will see for a follow-up question. *How*: it reads the thread's stored `summary` plus the most recent 20 messages from Supabase (fetched newest-first with `.order(...).limit(20)`, then `.reverse()`d back into chronological order), truncates each to 800 chars, and joins summary + recent turns into one string. This is the mechanism that gives a stateless model a sense of continuity. Anand: how are we handling it in terms of the agent (haiku) context window e.g. if the history is 1000 words then will is it fine given 300 token limit of Haiku?
- **`compactIfNeeded(threadId)`** — keeps memory from growing without bound by folding old turns into a running summary. *How*: it counts messages; if the thread has grown well past the window (and the summary isn't already caught up, tracked by `summary_upto`), it sends the older messages to a cheap model (Haiku, `temperature: 0`) with a "facts only, <150 words" prompt and stores the result back on the thread. Runs *after* replying so it never delays the answer (called with `.catch(() => {})` in fire-and-forget style). 🔒 The prompt deliberately keeps business facts/amounts/conclusions and drops style — losing a stated turnover or decision would corrupt later answers. Anand: so we using Haiku to compact the history? what is the limit ?
- **`POST(req)`** — the main handler; the whole request lifecycle lives here. *How, in order*:
  1. Parses `question` and optional `threadId` from the JSON body. If no `threadId`, it creates a new thread row (titled from the first 80 chars of the question) — so a fresh conversation gets an ID.
  2. Builds `context` from history *only* if this is a continuing thread, then inserts the user's message into Supabase.
  3. Opens a `ReadableStream` and returns it with SSE headers (`text/event-stream`, `no-cache`, `keep-alive`) — this is the **SSE streaming** mechanism: the connection stays open and the server pushes `data: {...}\n\n` lines as work happens.
  4. Inside the stream, `send(obj)` encodes any object as one SSE line. It first emits a `thread` event (so the UI learns the thread ID), then calls `askGSTPilot(question, {context, threadId, onStep})` — where `onStep` forwards each pipeline stage to the browser as a live `status` event.
  5. **Citation extraction**: after the answer comes back, it scans `r.reply` with a **regex** (`/\[([A-Z]+-[A-Z]+\/...)\]/g`) for inline source tags like `[CGST-ACT/s16]`, dedupes them via a `Set`, looks those chunk IDs up in the `legal_chunks` table, and builds citation objects (id + human-readable heading path + first 400 chars of the exact legal text).
  6. Saves the assistant message (with tier, citations, trace_id) and emits the final `answer` event carrying the reply, tier, and the `escalated`/`abstained` flags. Then fires `compactIfNeeded` and sends a `done` event.
  7. 🔒 Any thrown error is caught and streamed as a structured `error` event rather than crashing the stream — the user gets a clean failure, never a hang.

### `lib/agents/pipeline.ts`
This is the orchestrator — the "supervised team" that runs a question through every stage in a fixed order and enforces the safety gates between them. It produces both the final reply and an ordered **trajectory** (a step-by-step log) so automated evals can prove properties like "retrieval always ran before resolution."

- **`HAIKU`** — a constant pinning the exact cheap-model ID used for the reply-rewrite and verification steps. *How*: **model-in-a-closed-list** — hard-coding the ID keeps behavior/cost reproducible instead of drifting with a default.
- **`G2_MIN_RELEVANCE = 0.45`** — the retrieval-relevance floor (a cosine-similarity threshold). If even the best-matching law chunk scores below this, the question is treated as ungrounded. 🔒 Marked a placeholder pending Anand's tuning — it's the dial that decides "we have a real source" vs "abstain."
- **`TrajectoryStep` / `PipelineResult`** — the two core types. `TrajectoryStep` is one logged stage (`step`, `name`, `ok`, `ms`, optional `note`). `PipelineResult` is what the endpoint receives back: the `reply`, `traceId`, `tier`, `intent`, the `escalated`/`abstained` flags, and the full `trajectory`.
- **`REPLY_PROMPT(question, resolution)`** — builds the prompt that turns an approved internal resolution into a warm, plain reply. 🔒 *How*: the instructions are strict — keep every `[SOURCE-ID]` tag exactly where its claim sits, keep all numbers exactly, keep the literal abstain phrase if present, "no new information, only rephrase." This constrains the model to cosmetic rewording so it can't smuggle in unsupported claims.
- **`G5_PROMPT(reply, resolution)`** — builds the verification prompt for the final safety check. *How*: it asks a model to act as a checker and list every claim in the rewritten REPLY that isn't supported by the APPROVED resolution, outputting only `"PASS"` or a numbered list of violations. This is **model-verifying-not-generating** — checking is easier and safer than writing.
- **`PipelineOpts`** — the options bag: optional `context` (history), an `onStep` callback (the SSE bridge), and `threadId` (used as the Langfuse session ID).
- **`askGSTPilot(question, opts)`** — the single entry point that runs the whole flow. *How, stage by stage*:
  - **Tracing setup**: opens one Langfuse `trace` per turn with `sessionId = threadId`, so all a conversation's turns group into one session and every sub-step nests under it. A local `log(...)` helper appends each stage to `trajectory`, fires the `onStep` callback, and records a trace event — one function doing all three keeps the log, the live UI, and observability in lockstep.
  - **1. Intake + G1**: calls `classifyIntake(...)` (which runs **zod schema + enum validation** internally — G1) on the history-plus-question. 🔒 If `serviceError` is set (a transient API blip, *not* a real classification), it returns an honest "service busy, please retry" message rather than escalating a routine question to a CA. Otherwise it logs intake and G1 (with retry count; a double schema failure defaults to the safe T3 tier). Anand: G1 is Zod validation? 
  - 🔒 **T3 short-circuit**: if the tier is `T3` (notices/penalties/disputes), it immediately returns `caHandoff(...)` with `escalated: true` — proceedings go to a human CA and the question never reaches the language-model answer path.
  - **Router**: `reconcileLane(intake.intent, intake.lane)` picks the question's LANE (its type). *How*: a small `laneHandlers` map wires three lanes — `calculation`, `rate_lookup`, `change_over_time` — to their handler functions. If the chosen lane has a handler, it runs that lane inside its own trace span, tidies the reply (**regex** strips the internal `[SOURCE-ID]` placeholder and any leftover tag-only lines), and returns early. 🔒 The calculation lane specifically ASKS for a missing input or gives the cited general rule — never a bare abstention or an invented number.
  - **2+3. Retrieval + resolution**: for all other lanes it calls `answerQuestion(...)`, which does **hybrid search** (dense-vector + keyword, rank-fused) then grounded generation plus G4 (the citation gate), all nested under this turn's trace. It logs the top-3 retrieved chunk IDs.
  - **Clarify fallback**: if the query transform judged the question un-interpretable *and* nothing could be grounded, it returns a short generic "please be more specific" nudge instead of abstaining.
  - 🔒 **G2 relevance floor**: reads the best dense-retrieval score; if it's below `G2_MIN_RELEVANCE`, generation "ran on sand," so it abstains with a "no direct source found — confirm with a CA" message. This is the bar that stops confident answers built on weak matches.
  - **Logs resolution + G4**: records whether generation abstained and whether the citation gate passed (and whether a G4-triggered regeneration was used).
  - 🔒 **G3 recompute-don't-trust**: `recomputeNumbers(...)` re-verifies every figure in the draft against the cited text and calculator outputs. If a number fails, it regenerates once with the specific violations fed back in; if it *still* fails, it replaces the answer with an abstention. No figure is trusted just because the model wrote it.
  - **4. Reply synthesis + G5**: unless the draft is already an abstention, it rewrites the resolution into a warm reply via `REPLY_PROMPT` (Haiku, `temperature: 0`, wrapped in `recordGeneration` for token logging), then runs the `G5_PROMPT` check on that candidate. 🔒 **G5 failure policy**: if the check doesn't start with `"PASS"`, it *ships the already-safe APPROVED draft* instead of the prettier-but-possibly-leaky rewrite — "tone is never worth a fabricated claim." The whole reply layer is wrapped in `try/catch`: if it throws, it ships the safe draft as-is, because the cosmetic layer must never block a correct answer.
  - **Final tidy + return**: a last **regex** pass strips any literal `[SOURCE-ID]` the reply model may have echoed and fixes spacing, updates the trace output, flushes Langfuse, and returns the `PipelineResult`. Every early-return path also flushes the trace first, so no turn is lost from observability.

## 2 · Intake & Router

### `lib/agents/intake.ts`
The **intake agent** — the very first step in the pipeline. It takes a raw seller question and, in a single cheap model call, classifies three things: *intent* (what kind of question), *tier* (how risky), and *lane* (which handler should answer). Its output is machine-checked so nothing downstream ever trusts a malformed classification.

- **`IntakeSchema` / `Intake`** — the exact shape every classification must have: an `intent` from a fixed list, a `tier` of `T1`/`T2`/`T3`, a `lane` from a fixed list, and a short `reason` (capped at 300 chars). *How:* a **zod schema** (a runtime rule-checker for data shape) — `z.enum` forces each field to be one of a closed list of allowed values, so the model literally cannot return a tier or lane the system doesn't recognize. 🔒 This is safety gate **G1**: "parse, don't trust" — invalid model output is rejected, not passed along.
- **`PROMPT(q)`** — builds the instruction text sent to the model. *How:* a template that inlines the allowed intents/lanes (as JSON so the model sees the exact vocabulary), the tier rules, the `LANE_GUIDE` guidance block, and the user's question. Two safety-shaping instructions stand out: "when torn, pick the HIGHER tier" and a definition of `out_of_scope`, both nudging the model to escalate rather than under-classify.
- **`anthropic` / `sleep`** — a lazily-created API client (built once, on first call) and a tiny helper that pauses execution for a given number of milliseconds (used for retry backoff).
- **`isTransient(e)`** — decides whether an error is a temporary *service* hiccup versus a real *classification* failure. *How:* inspects the error's HTTP status (429/408/5xx), its `name`, and its `message` with a **regex check** for words like "timeout", "network", "overloaded". 🔒 This distinction is a safety bar: a network blip must never be mistaken for a risky question and wrongly escalated.
- **`classifyIntake(question, parent)`** — the main exported function: runs intake and gate G1, returning the validated `Intake` plus how many parse-retries happened and whether the service failed. *How:* a **retry loop** (up to 4 attempts) calling the Haiku model at `temperature: 0` (deterministic) with a 300-token cap so a long `reason` can't truncate the JSON. Each response is stripped of ``` fences, `JSON.parse`d, then run through `IntakeSchema.parse`. Two failure paths are handled *differently*:
  - Transient errors → wait with increasing backoff (0.5s, 1s, 1.5s) and retry.
  - Genuine parse/validation failures → re-ask exactly once, then stop.
  🔒 The two exits encode the core abstention/escalation rule: if only the *service* failed, it returns a `serviceError` flag with a harmless "try again" placeholder (T1, out_of_scope) — never a fake escalation. If the *model output* stays unparseable, it **fails UP the ladder to T3 / `escalate`** with an honest reason, so an unclassifiable question meets a human CA rather than getting a confident wrong answer.
- **`caHandoff(question, intake)`** — produces the human-readable handoff message shown when a question escalates to a CA (chartered accountant). *How:* assembles a fixed Hindi/English summary (question, category, tier, why-escalated, a deadline warning) as joined lines. 🔒 By design it is a *factual summary only, never legal advice* — the escalation safety bar in text form.

### `lib/agents/lanes.ts`
The **lane vocabulary and routing helpers**. It defines the question *types* the router sorts every question into, the guidance text the classifier reads, and two small deterministic correctors that fix or refine the model's lane choice. It deliberately holds only vocabulary + guidance — the actual lane handlers and the router live elsewhere (`pipeline.ts`).

- **`LaneOutcome`** — the common return shape every lane handler hands back to the pipeline. *How:* a type with `reply`, `abstained`, `mode` (a short free-text trajectory tag like "compute" or "ask-condition"), `citationIds` (which feed the SOURCES panel), and `note`. 🔒 The comment pins down a subtle safety rule: `abstained` is `true` **only** for an honest "I can't answer" — asking for a missing input or offering to compute is *not* an abstention, so genuine helpfulness isn't miscounted as a refusal.
- **`LANES` / `Lane`** — the closed list of the seven lane names (`rate_lookup`, `calculation`, `procedure`, `eligibility`, `change_over_time`, `escalate`, `out_of_scope`) with an inline comment defining each. *How:* a **`const` array marked `as const`** so the values are frozen and become a precise union type; `Lane` is derived from it. This single source of truth is what `intake.ts` imports to constrain the model's `lane` field. Note `escalate` mirrors tier T3 and `out_of_scope` mirrors the out-of-corpus case.
- **`LANE_GUIDE`** — the guidance block injected into the intake prompt so *one* model call classifies intent, tier, and lane together. *How:* a template string of short "trigger → lane" discriminating rules with concrete examples, telling the model to default to `procedure` for explanatory questions. Kept deliberately terse because long taxonomies make small models waffle.
- **`reconcileLane(intent, modelLane)`** — a deterministic guard that corrects the model's lane pick using the more-reliable intent. *How:* "**model proposes, code corrects**." If the model committed to a *specific* actionable lane (`calculation`, `rate_lookup`, `change_over_time`) it's trusted as-is — those picks mean it read the question shape well. Otherwise, a strong intent pulls a vaguely-classified question into the right lane (e.g. `late_fee_interest` → `calculation`, `registration` → `calculation` since the threshold tool handles it). This exists because the classifier nails *intent* but wavers on *lane* for generally-phrased questions — and it prevents wrongful abstentions by steering such questions to a lane that offers to compute instead of a RAG path that might force-abstain.
- **`pickCalcTool(question, context, intent)`** — for a `calculation`-lane question, picks which of the three registered calculator tools to run. *How:* cheap **keyword/intent regex matching** (no model call, so it's cheap and easy to debug): a registration signal (`register`, `gstin`, `threshold`, `turnover limit`, or `intent === "registration"`) → `registration_threshold`; interest words (`interest`, `section 50`, `byaaj`) → `delayed_payment_interest`; everything else falls through to the default `gstr_late_fee`. Matching runs on the lowercased context + question combined.

## 3 · The ASK move & Tool Registry

### `lib/agents/clarify.ts`
This file adds the agent's third move — **ASK** — for questions that are answerable in principle but missing an input (e.g. a late-fee question with no dates). Instead of abstaining, it reads a tool's required-input schema, pulls whatever the conversation already supplied, and if a required input is still missing, asks one bundled friendly question for the gaps.

- **`SlotFill`** (type) — the outcome of trying to fill a tool's inputs. Holds `values` (the inputs confidently extracted, keyed by slot name) and `missing` (the required slots still empty). The invariant is simple: `missing.length === 0` means the tool can run now; otherwise those slots are exactly what to ask for.
- **`EXTRACT_PROMPT`** (const, a function returning a string) — builds the instruction sent to the cheap extractor model. *How:* it interpolates the tool's purpose, the current date, and a per-slot list describing each input's expected kind (enum options / ISO date / boolean / expanded number). It hard-codes the messy real-world normalization rules — resolve relative dates ("kal", "5 din pehle") to absolute ISO dates using *today*, expand "10 crore"/"2 lakh" to plain digits, map "haan"/"nahi" to true/false — and demands **JSON-only** output with `null` for anything the user never stated. 🔒 The "use null, NEVER invent a date/amount/choice" instruction is the anti-fabrication bar at the prompt level.
- **`anthropic`** (module-level `let`) — a lazily-created, reused Anthropic SDK client. *How:* starts `null` and is initialized once on first use (`anthropic ??= new Anthropic()`), so the client isn't constructed at import time.
- **`fillSlots`** (exported async function) — the "model proposes, code disposes" extractor. *How:* it stitches prior context and the current question into one `convo` string, computes `today`, calls the cheap Haiku model at `temperature: 0` (wrapped in `recordGeneration` for Langfuse tracing), strips any ```` ```json ```` fence, and `JSON.parse`s the reply. Each parsed value is run through `validate` before being trusted; only values that pass are kept. 🔒 Two safety layers: (1) every extracted value must survive type validation, and (2) the whole body is wrapped in `try/catch` so **any** model or parse failure falls through to empty `values` — which then reports every required slot as missing, so a broken extractor degrades into *asking*, never into a wrong number. Finally it computes `missing` as the required slots not present in `values`.
- **`validate`** (internal function) — the trust boundary in code: returns a cleaned value or `null` (meaning "not usable, treat as not given"). *How:* a `switch` on the slot's `type`. Dates must match a `yyyy-mm-dd` regex **and** parse as a real date; numbers must be finite (with a deterministic word-amount backstop — regex-detects crore/lakh/करोड़/लाख, strips commas/₹, multiplies by 1e7/1e5 — in case the model echoes "10 crore" verbatim); booleans must be actual booleans; enums must case-insensitively match one of the declared options, returning the canonical spelling. 🔒 By returning `null` on any mismatch, it always fails toward "ask" rather than "compute on a mis-read".
- **`buildClarification`** (exported function) — pure formatting: turns the missing slots into one warm, bundled Hinglish question. *How:* it maps each missing slot to a bullet (`- <ask>`), inlining enum options as a `(A / B / C)` menu so choice slots read like a menu not an interrogation; it capitalizes the tool's `purpose` as the "I can do that —" opener and appends a "tell me in one message" closer. 🔒 Called out in the code: this text is a **question, not a legal claim**, so it carries no citation and never touches the citation gate — asking for input is not asserting law.

### `lib/tools/registry.ts`
This file is the single, central declaration of what each deterministic tool needs to run. It is the **schema the ASK move reads**: when a lane routes a question to a tool, that tool's still-missing required slots *are* the questions asked — so adding a new tool automatically teaches the clarifier what to ask, with no per-tool hand-written prompts.

- **`SlotType`** (type) — the closed set of input kinds a slot can be: `"date" | "number" | "boolean" | "enum"`. This is the same list `validate` switches on, keeping schema and validator in lockstep.
- **`SlotSpec`** (type) — one input a tool needs. Fields: `name` (machine key that must match the calculator's input field exactly), `ask` (the friendly phrase shown in the clarification), `type` (drives validation), `required` (only missing required slots trigger a clarification), optional `options` (enum choices — both offered to the user *and* enforced on extraction), and optional `example` (a concrete value shown to the extractor to anchor formatting).
- **`ToolSpec`** (type) — one tool's declaration: `name`, a one-line `purpose` (shown to the extractor so it knows what it's filling, and reused as the "I can do that —" opener of a clarification), its `slots`, and an optional `generalRule`. *How the rule works:* `generalRule` is the tool's standing rule pre-written **with its own citations** — used as the lead answer when the user hasn't given inputs yet; because it's deterministic and already cited (the rule is literally the constants the calculator applies), 🔒 it never depends on retrieval or the citation gate. Tools without a tidy standing rule omit it and fall back to the RAG path.
- **`TOOL_SPECS`** (exported const) — the registry itself: a `Record` mapping tool name → `ToolSpec`, holding the three Phase-6 calculators. Their slot `name`s deliberately mirror the function inputs in `lib/calculators/index.ts` exactly, so the registry and the calculator code can't drift (the extractor fills these names; the calculator reads the same names). The three entries:
  - **`gstr_late_fee`** — late-fee calculator; `generalRule` states the ₹50/day (₹20 nil) rule and turnover-based caps with citations (`[CGST-ACT/s47]`, `[NOTIF-CT/nt-2021-019]`). Five required slots: `return_type` (enum: GSTR-3B / GSTR-1 / GSTR-9), `due_date`, `filing_date`, `nil_return` (boolean), `annual_turnover_inr` (number, to pick the right cap).
  - **`delayed_payment_interest`** — section-50 interest calculator; `generalRule` states the 18%-per-annum simple-interest rule (`[CGST-ACT/s50]`). Three required slots: `tax_amount_inr`, `due_date`, `payment_date`.
  - **`registration_threshold`** — GST-registration check; `generalRule` covers the ₹40 lakh goods / ₹20 lakh services limits (and special-category ₹20/₹10 lakh) plus the e-commerce/inter-state compulsory-registration carve-out (`[CGST-ACT/s22]`, `[CGST-ACT/s24]`). Three required slots: `annual_turnover_inr`, `supply_type` (enum: goods / services / both), `special_category_state` (boolean).

## 4 · The Lanes

### `lib/agents/lanes/calculation.ts`
The calculation lane handles questions that need a specific number ("what late fee will I owe?"). It is the first lane to use the ASK move end-to-end: it picks a calculator, extracts inputs from the conversation, and branches into compute-exact / give-general-rule-and-offer / honest-handoff — so a calculation question never dead-ends in an abstention.

- **`runCalculationLane`** — the whole lane, and the entry point. It calls `pickCalcTool` to choose a calculator, then runs a fit-check (`toolFits`); if nothing fits it tries plain arithmetic and finally falls back to the RAG path. Otherwise it uses `fillSlots` to pull the calculator's required inputs from the question + prior conversation, and branches: GSTR-9 late fee → general rule (wrong formula, handled honestly); any missing input → `generalPlusOffer`; all inputs present → runs the matching deterministic calculator (`gstrLateFee` / `registrationThreshold` / `delayedPaymentInterest`) and returns an exact, pre-cited reply. 🔒 The compute path is "model proposes, code disposes" — the number is computed in code and carries the calculator's own legal-basis citation ids, so it's grounded without ever touching the citation gate.
- **compute replies (inline)** — each branch builds a multi-line Hinglish reply string: the headline number, a line showing the formula/breakdown tagged with a real citation like `[CGST-ACT/s47]`, and an echo-back of the user's own inputs ("Galat ho to sahi bata dein" — "if wrong, correct me"). 🔒 The inline `[...]` tags are the citations; every legal line names its source section/notification. Numbers are formatted with `toLocaleString("en-IN")` for Indian digit grouping.
- **`generalPlusOffer`** — the "never a dead-end" helper: gives the general cited RULE, then appends a bundled offer to compute the exact figure once inputs arrive. *How:* if the tool has an encoded `generalRule` string it uses that directly and harvests citation ids from it with a regex over `[ACT-PART/id]` patterns; otherwise it calls the RAG path (`answerQuestion`) for a grounded general answer. 🔒 It sets `abstained: false` on purpose — offering to help is explicitly not an abstention — and if even RAG can't ground it, it still leads with an honest one-liner rather than refusing.
- **`toolFits`** — a guard that checks whether the picked calculator actually matches the question, so a plain-math question doesn't get answered with the late-fee tool (the default). *How:* lowercases context+question and applies regex/intent rules — refund → false (its formula lives in RAG), registration/interest/late-fee each require their own keyword or intent signal ("model-in-a-closed-list" style whitelist per tool).
- **`tryGeneralMath`** — handles plain arithmetic ("2 lakh ka 18%") by extracting ONE operation and computing it exactly. *How:* a cheap Haiku model call (temperature 0) returns strict JSON `{op, values, label}` — or `{"op":"none"}` — the code strips any code-fence, `JSON.parse`s it, and dispatches to the safe `generalArithmetic` calculator; any failure or non-calculation returns `null` so the lane falls through to RAG. 🔒 No citation attached and no `eval` — the operation is chosen from a closed list of ops and the rate came from the user, so the result is arithmetic on their numbers, not a claim about the law. The Anthropic client is lazily created once (`anthropic ??= new Anthropic()`), and the call is wrapped in `recordGeneration` for Langfuse tracing.
- **`cap`** — tiny helper that capitalizes the first letter of a label string.

### `lib/agents/lanes/rate.ts`
The rate lane answers "what's the GST rate for X?" as a looked-up FACT. It resolves the item (English or Hindi), looks up the rate, and either answers pre-cited, ASKS a price-threshold question for conditional items (footwear/apparel), or abstains honestly when the item isn't in the table.

- **`CONFIRM`** (const) — a fixed honesty line ("confirm the notification for your exact product/variant") appended only to conditional or unverified entries, not to simple/exempt ones.
- **`runRateLane`** — the whole lane. *How:* calls `resolveItem` to map the phrasing to a table entry; if none, 🔒 returns an honest abstention (`abstained: true`) rather than guessing a rate. Then `lookupRate` returns one of three kinds: `ask` → the ASK move, returns the item's threshold question because the rate depends on a price band it doesn't know; `resolved`/`exact` → builds a condition suffix (below/above the ₹ threshold) and returns the pre-cited answer via `buildRateReply`. 🔒 Each answered reply carries `entry.citation` as its citation id, so the rate is grounded by the table itself and never depends on retrieval phrasing or the citation gate.
- **`buildRateReply`** — assembles the pre-cited answer string. *How:* names the item + rate, adds the notification in prose plus its effective date, tags the real chunk id in `[...]` so the SOURCES card resolves, and appends the `CONFIRM` hedge for conditional or unverified entries. 🔒 A 0% rate is phrased as "exempt (0%)" rather than "0% tax" — a deliberate wording safety choice so an exemption isn't mistaken for a taxable-but-zero claim.
- **`cap`** — capitalizes the item name for display.

### `lib/agents/lanes/timeline.ts`
The change-over-time lane answers "has the footwear rate changed in the last N months?" It is bounded and honest: it only narrates a "change" when the corpus actually holds two or more DATED documents on the topic, and otherwise says so plainly rather than inventing one.

- **`parseWindowMonths`** — reads how far back to look from the question. *How:* readable regex rules over "6 months" / "2 saal" / "since 2023" / "last year" (English and Hindi), converting years to months and "since YEAR" to a month count from today; defaults to 24 months when unspecified.
- **`runTimelineLane`** — the whole lane. *How:* computes a date cutoff from the window, runs `hybridSearch` (dense-vector + keyword retrieval, rank-fused) to get candidate chunk ids, then queries Supabase for each chunk's `effective_date`, `act`, and source doc. It keeps only dated notifications/circulars (`NOTIF-CT`, `NOTIF-CTR`, `CIRCULAR`), de-duplicates to one row per source document via a `Map` keyed on `source_doc_id` (a notification split across pages counts once), and sorts oldest→newest by date string. It also seeds the item's governing rate notification from the rate table (`resolveItem`) since retrieval often buries it. Then it branches on how many dated docs fall inside the window.
- **branch: ≥2 docs in window** — 🔒 the only case allowed to be narrated as a "change": it lists each dated doc as a cited timeline line `[chunk-id]`, oldest→newest, with every line tagged to a real chunk id so it's verifiable.
- **branch: exactly 1 doc in window** — honest "just this one document" reply, not a false "no change."
- **branch: 0 in window but topic is held** — honest "no change in that window," pointing at the most recent related document.
- **`insufficient`** — 🔒 the fallback when fewer than two dated docs exist at all: returns `abstained: true` and refuses to build a timeline, explicitly declining to fabricate a change to look helpful.
- **`cap`** — capitalizes a heading label for display.

## 5 · Rates & Calculators

### `lib/rates/table.ts`
The rate table: GST rates stored as structured, self-citing **FACTS** rather than sentences buried in a multi-page notification PDF. It exists because page-chunking often separates an item from its percentage ("dilution"), so retrieval finds the item but loses the number — a clean lookup table fixes that and works language-agnostically (Hindi item words resolve via synonyms).

- **`RateTier`** (type) — one row of a price-conditional rate: an optional `upto`/`above` boundary and the `rate` that applies on that side. Used as the two-element ladder for items whose rate depends on price.
- **`RateCondition`** (type) — describes a price-conditional item (footwear, apparel). Holds the exact `ask` question to put to the user, the `unit` ("per pair"), the ₹ `threshold`, and the `tiers` ladder. This is the data behind the rate lane's ASK move.
- **`RateEntry`** (type) — one item's full record: canonical `item` name, `synonyms` (English + Hindi/Hinglish a seller might type), indicative `hsn` code, either a flat `rate` or a `condition`, plus the citation trio (`source_notif`, `citation` chunk id, `effective_date`) and a `verified` flag. 🔒 Every entry carries a real `citation` chunk id and a human-readable notification number so a rate answer always names its legal source. `verified: false` honestly flags that the table is model-compiled and unchecked against source PDFs.
- **`N2017` / `N2025`** (consts) — two reusable citation bundles (the original 2017 rate schedule and the Sept-2025 "GST 2.0" revision). Spread into entries with `...N2017` so each item inherits the right notification number, chunk id, and effective date without repetition.
- **`RATE_TABLE`** (const) — the hand-authored array of ~30 `RateEntry` records, grouped by slab (price-conditional, 5% goods, 18% goods, other slabs). The single source of truth for rates.
- **`RATES`** (const) — `RATE_TABLE` with the stray placeholder (the entry with no synonyms) filtered out, so only matchable items survive.
- **`RATE_ITEMS`** (const) — just the canonical `item` names pulled from `RATES`. 🔒 This is the **closed list** handed to the model resolver so it can only pick a real table item and never invent one ("model proposes, table disposes").
- **`findBySynonym`** — finds the entry whose synonym appears in the user's text. *How:* lowercases the text, pads it with spaces, and does a substring scan over every synonym (word-boundary padded to prefer whole-word hits). Deterministic and instant — tried before any model call, and it catches common Hindi/English words directly. Returns `null` on no match.
- **`findByItem`** — looks up an entry by exact (case-insensitive) canonical name. *How:* used to confirm the model's pick is genuinely in the table before trusting it; returns `null` if not found.

### `lib/rates/lookup.ts`
Turns a user's phrasing ("chappal ka rate?") into a table entry and then into a pre-cited rate. Two model touches, both "propose from a **closed list**, code confirms," so the model can never fabricate an item or a number — the rate itself is always read from the table, never generated.

- **`anthropic`** (module-level const) — a lazily-created Anthropic SDK client, initialized on first use (`anthropic ??= new Anthropic()`) and reused across calls so the client isn't rebuilt every time.
- **`resolveItem`** — maps the user's words (English or Hindi) to a canonical table item. *How:* tries deterministic `findBySynonym` on the question (then the context) first — free and instant. Only on a miss does it make one cheap Haiku call that must pick exactly one name from the `RATE_ITEMS` closed list (or reply "none"), with `temperature: 0` for consistency. 🔒 The model's answer is re-checked through `findByItem`, so a hallucinated name resolves to `null`; on any error or no match it returns `null` and the lane **abstains** honestly rather than guessing.
- **`RateLookup`** (type) — the three shapes a lookup can return: `flat` (a fixed rate), `resolved` (a conditional rate once the price side is known, tagged `below`/`above`), or `ask` (we still need the threshold answer from the user).
- **`lookupRate`** — given an entry, produces the rate. *How:* flat items return their `rate` immediately. Conditional items call `resolveConditionSide` to learn which side of the ₹ threshold the product is on; if unknown it returns `ask` (triggering the rate lane's ASK move), otherwise it picks the matching tier from the ladder and returns `resolved`. 🔒 The rate is looked up from the entry's `tiers`, never computed by the model.
- **`resolveConditionSide`** — reads from the conversation whether the product's per-unit value is at/below or above the threshold. *How:* one Haiku call with a **closed answer set** — only "below", "above", or "unknown" — at `temperature: 0`. 🔒 A vague or silent question safely yields "unknown", so the system asks rather than guesses; a model reads the value (handling "kam"/"zyada"/"under 2500"/"3000 rupees" across languages) instead of a brittle regex, and any error falls back to "unknown". Both model calls are wrapped in `recordGeneration` for Langfuse observability (logging model, input, and token usage).

### `lib/calculators/index.ts`
Deterministic money math — "the model proposes, code disposes." The agent extracts parameters from the conversation and **calls** these functions; it never does arithmetic in prose (a model doing math is just sampling likely-looking digits, and gets off-by-one date errors dangerously often). 🔒 Every legal figure returns `citation_ids` so the agent can cite the math's legal basis, not just the output.

- **`LateFeeResult`** (type) — the shape returned by the late-fee calc: days late, per-day fee, computed fee, any cap applied, final payable, `citation_ids`, and a plain-English `explanation`.
- **`gstrLateFee`** — computes the GSTR-3B/GSTR-1 late fee under s47. *How:* converts both dates to milliseconds, subtracts, and divides by a `msPerDay` constant to get whole `days_late` (the day-counting rule written **once**, reviewed once, tested — clamped at 0 so early filing never goes negative). Picks ₹20/day (nil return) or ₹50/day, applies a turnover-linked cap (₹500 / ₹2,000 / ₹5,000 / ₹10,000 via a chained ternary), and returns `min(computed, cap)`. 🔒 Carries the s47 + notification `citation_ids`.
- **`InterestResult`** (type) — shape for the interest calc: days, rate percent, interest amount, `citation_ids`, `explanation`.
- **`delayedPaymentInterest`** — interest on delayed tax payment under s50(1). *How:* same exact date-diff to get `days`, then simple day-wise interest: `tax × 18 × days ÷ (100 × 365)`, rounded to a whole rupee. 🔒 Cited to `CGST-ACT/s50`.
- **`ArithmeticResult`** (type) — shape for general math: the `op`, the cleaned `values`, a nullable `result`, an `explanation`, and an optional `error`.
- **`generalArithmetic`** — the safe replacement for "the model does math in prose." *How:* a fixed **dispatcher** (a `switch` over a closed set: `multiply`, `sum`, `subtract`, `divide`, `percent_of`) — 🔒 explicitly **never `eval()`**, so there's no code-injection surface and nothing but arithmetic can run. It coerces inputs to numbers and drops non-finite ones, returns a structured error for empty input / divide-by-zero / wrong arg count / unknown op, and rounds to 2 decimals. Carries **no** citation, because "value × rate" is math, not law.
- **`RegistrationResult`** (type) — shape for the registration check: applicable `threshold`, whether it `crosses`, `must_register`, `citation_ids`, `explanation`, and a `caveat`.
- **`registrationThreshold`** — decides whether a seller must register under s22. *How:* selects the aggregate-turnover threshold from supply type and special-category-state status (₹40L/₹20L goods, ₹20L/₹10L services, "both"/services taking the lower one), compares turnover against it, and returns the result. 🔒 Cites s22 + s24 and always attaches the e-commerce/inter-state `caveat` (those sellers must register regardless of turnover), so the rule lives in code once, not in model memory.
- **`RefundResult`** (type) — shape for the export-refund calc: `refund`, `citation_ids`, `explanation`.
- **`refundExportRule89`** — the Rule 89(4) export-refund formula: `Refund = (Zero-rated turnover × Net ITC) ÷ Adjusted Total Turnover`. *How:* guards against a zero/negative denominator (returns a 0 refund with an explanatory message) before computing the exact rounded figure. 🔒 Cited to `CGST-RULES/r89`; a formula the model must never approximate.

## 6 · RAG & Retrieval

### `lib/agents/answer.ts`
This is the RAG "resolution" path: it takes a question, retrieves law chunks, has a pinned Claude model write a fully-cited answer (using calculator tools for any money math), then runs a deterministic citation gate that either passes the answer, forces one targeted rewrite, or abstains. It is the safety-critical heart of the free-text answering flow.

- **`GENERATION_MODEL`** — the exact model id (`claude-sonnet-4-6`) used for writing answers, held in one named constant. 🔒 Pinned on purpose: the comment notes changing it is an "eval'd migration", so answer quality never drifts silently under you.
- **`AnswerResult`** (type) — the shape of what this module returns: the `answer` text, whether it `abstained`, the list of `citations`, the raw `gate` result, whether it `regenerated`, the underlying `retrieval`, and a `needsClarification` flag. Acts as the contract every caller reads against.
- **`TOOLS`** (const) — the five calculator tools offered to the model, each as an Anthropic tool definition with a name, a "ALWAYS use this instead of doing it yourself" description, and a strict `input_schema` (a JSON schema listing typed, required parameters). 🔒 This is how money math is forced into deterministic code: the model must call `gstr_late_fee`, `delayed_payment_interest`, `general_arithmetic`, `registration_threshold`, or `refund_export_rule89` rather than compute amounts in prose (where it could hallucinate).
- **`SYSTEM`** (const) — the system prompt that governs the answer-writer. It encodes the four safety rules as English instructions: cite every legal claim with a bracket tag from the provided sources, abstain with an exact phrase when sources don't cover it, describe options rather than dictate, and flag conflicting sources. 🔒 Rules 1 and 2 are the citation and abstention bars stated to the model; it also bans markdown headings/tables (so every sentence stays independently checkable) and forces numbers-in-digits.
- **`GEN_SOURCE_CHARS`** (const) — the per-chunk character cap (12,000 ≈ 3k tokens) applied to source text before it goes into the prompt. The comment explains the tradeoff: large enough that a big section (like the refund procedure) arrives whole, small enough that eight sources fit a sane prompt budget; it was raised from 4,500 because that truncated the sub-rule specifics the answer needs.
- **`sourcesBlock`** — fetches the full text of the retrieved chunk ids from Supabase and formats them into `<source id="…" heading="…">…</source>` blocks for the prompt. *How:* it queries the `legal_chunks` table by the fused ids, builds a `Map` from id→row for lookup, slices each chunk to `GEN_SOURCE_CHARS`, and also returns a `chunkTextById` map so later steps (like fact-matching) can read the same full text the model saw. Generation reads full text, not the 200-char list snippets — you cannot ground an answer in a preview.
- **`generate`** — runs the model with a bounded tool-use loop and returns the final text plus the citation ids vouched by any calculators. *How:* a `for` loop of up to 4 rounds (recursion/tool loop) calls `anthropic.messages.create` at temperature 0; if the model stops normally it returns the joined text, but if `stop_reason` is `tool_use` it executes the requested calculator in code, appends the JSON result back as a `tool_result` message, and loops. 🔒 Two safety mechanisms: calculators return their own legal-basis `citation_ids`, which are collected as "code-vouched" allowed citations; and if the loop never terminates within 4 rounds it returns the abstain phrase rather than an unfinished answer.
- **`ResolveExtras`** (type) — the extra payload (`toolOutputs`, `chunkTextById`) bundled alongside `AnswerResult` so downstream code gets both the calculator outputs and the full chunk text without re-fetching.
- **`answerQuestion`** — the exported orchestrator that runs the whole resolution: retrieve → build prompt → generate → citation gate → (one named-error regeneration) → prune-or-abstain, with Langfuse tracing throughout. *How, step by step:*
  - Calls `hybridSearch` for the chunks, then `sourcesBlock` to build the prompt; assembles `baseMessages` containing the sources, optional conversation `context`, the user's question, and any `extraFeedback` from a prior attempt.
  - Runs `generate` once, then computes `allowedIds` = the retrieved chunk ids **plus** the calculator-vouched ids, and calls `verifyCitations(answer, allowedIds)` — the deterministic gate.
  - 🔒 If the gate fails, it builds a *named-errors* message ("the tag [X] is NOT among your sources", "this claim has no citation tag: …", "your ONLY allowed tags are …") and regenerates exactly once. Naming the specific failures turns a blind resample into a targeted edit, which models fix far more reliably.
  - 🔒 If the gate still fails, it does **not** discard everything: `pruneUngrounded` drops only the ungrounded/fake-cited sentences and keeps the properly-cited remainder; full abstention happens only if no grounded claim survives, in which case it returns the abstain phrase plus a "consult a CA" line. The invariant it protects: no uncited or invented-citation claim ever reaches the user.
  - `abstained` is true only when the whole answer is a refusal (contains the phrase AND cites nothing) — using the phrase for one sub-point is a partial answer, not an abstention.
  - Tracing is best-effort and nests under the pipeline's trace when called in-pipeline (or creates its own when standalone, e.g. an eval); it scores the trace `citation_gate` = 1/0 and flushes only when it owns the trace. Observability never blocks answering.

### `lib/retrieval/transform.ts`
Query transformation that runs *before* retrieval: it turns a seller's messy question into search-ready inputs using two layers — a deterministic regex reference parser, and one cheap Claude (haiku) pass that rewrites vocabulary and generates a fake "hypothetical answer" to search with. It fails soft, always degrading to the raw query rather than blocking.

- **`Transformation`** (type) — the output contract: `rewritten` (statute-vocabulary version for keyword search), `hyde` (a hypothetical answer for dense search, or `null`), `exact_tokens` (verbatim-verified identifiers), `needs_clarification`, `doc_type_hint` (`statute`/`stream`/`any`, which drives the statute boost), and `direct_ids` (identity references).
- **`parseReferences`** — deterministically extracts chunk ids from phrases like "section 16(4) of CGST act" or "rule 86A". *How:* regex matching (no model) collects section and rule numbers into a `Set` (dedupes), decides CGST vs IGST by testing for the word "igst", strips subsection brackets (chunks are whole sections), and returns ids like `CGST-ACT/s16` or `CGST-RULES/r86A`. This is the "deterministic wins where it can — free, instant, cannot hallucinate" layer for identity lookups.
- **`TRANSFORM_PROMPT`** (const) — the haiku prompt template that asks for strict JSON with `rewritten`, `exact_tokens`, `hypothetical_answer`, `needs_clarification`, and `doc_type_hint`. It bakes in domain expansions (TCS → collect tax at source, Amazon/Flipkart → electronic commerce operator, translate Hinglish) and precise definitions of statute vs stream.
- **`transformQuery`** — the exported transformer: runs the regex parser, then one haiku call, and assembles the `Transformation`. *How:* it prepares a `fallback` object equal to the raw query up front, calls the model at temperature 0 asking for JSON, strips code fences and `JSON.parse`s it, and validates each field defensively (rewrite must be non-trivial length, hyde must be >20 chars else `null`, doc_type_hint must be in the allowed list — model-in-a-closed-list). 🔒 The trust boundary: each `exact_token` is kept only if it appears as a substring of the raw question (`lowerQ.includes(...)`), so the model can echo what the user actually typed but can never mint a new identifier (e.g. invent a section number). Any exception falls back to the raw query — degraded, never blocked.

### `lib/retrieval/search.ts`
The single entry point for all retrieval: it transforms the query, embeds it, runs two search channels plus a fusion query in Postgres, pins any directly-referenced sections, and records a trace row. Routing every caller through one function is what makes the admin Traces view a complete flight recorder.

- **`RETRIEVAL_CONFIG`** (const) — the retrieval knobs in one visible place: `rrf_k: 60` (the Reciprocal Rank Fusion dampener, `1/(60+rank)`, which stops the #1 hit from dominating), `channel_top_n: 20` (candidates per channel), `final_top_n: 8` (chunks handed to the agent), and the embedding `model`. These values are also written into every trace.
- **`ChannelHit` / `FusedHit` / `SearchResult`** (types) — the shapes of a single per-channel hit, a fused hit (carrying its dense rank, keyword rank, and `rrf_score`), and the overall result (transformation used, both channels' hits, the fused list, per-stage timings, and a `traceId`).
- **`hybridSearch`** — the exported function that does retrieval end to end. *How, in order:*
  - Step 0: calls `transformQuery`. Both channels then run on the *rewritten* text; the original is preserved in the trace.
  - Chooses inputs per channel: the dense (meaning) channel embeds `hyde ?? rewritten` (the hypothetical answer when available, since corpus text looks like answers); the keyword channel gets `rewritten` plus the verbatim `exact_tokens` joined together.
  - Sets `statuteBoost` to 1.5 when `doc_type_hint === "statute"` (else 1.0), applied inside the fusion SQL *before* the top-8 cut so a crowded-out anchor section (e.g. s54 for refunds) can climb into the set; rate/notification questions keep 1.0 because there the notification is the authority.
  - Embeds the dense input once via `getEmbedder().embed(...)` and JSON-stringifies the vector for Postgres.
  - 🔒 Runs the three read-only Postgres RPCs (`dense_search`, `keyword_search`, `hybrid_search`) in parallel with a retry loop — up to 3 attempts with growing backoff (2s, 4s) — so transient network blips during long eval/agent runs don't fail the whole search.
  - 🔒 If the transformation produced `direct_ids`, it fetches those chunks by id filtered to `status = 'in_force'` and **pins** them above the fused results (deduplicated), with a sentinel `rrf_score` of 1. Ids that don't exist are silently dropped — "the parser can guess, the database decides." This is how an explicit "section 52" reference beats mere similarity, and how repealed provisions are excluded.
  - Assembles `SearchResult` with ranked channel hits (`withRank` numbers them 1..n) and per-stage timings, then records a trace row into `retrieval_traces` (config, timings, both channels, and the fused ids). 🔒 The trace insert is wrapped in try/catch — "a broken flight recorder must not break search itself" — so tracing never blocks the returned result.

### `lib/retrieval/embed.ts`
The embedding provider — the piece that turns text into a 1024-number vector so similar meanings land near each other. It hides one swappable interface over a local BAAI bge-m3 model run through Transformers.js, so there is no API and no per-token cost.

- **`EmbeddingProvider`** (interface) — the one-method contract (`embed(texts) → number[][]`). The abstraction is deliberate: a paid embedding API could slot in later without touching any caller. bge-m3 is symmetric, so the same call embeds both queries and documents.
- **`extractor`** (module-level var) — a cached, lazily-created pipeline handle. Because the model takes seconds to load, it is created once and reused (critical for the Playground, where each request would otherwise re-pay the load cost).
- **`LocalBgeM3`** (class) — the concrete provider. *How:* on first `embed` it lazily loads the `feature-extraction` pipeline for the pinned model id/revision using `q8` quantized weights (~4× smaller/faster on CPU, negligible quality loss), then runs the texts with `cls` pooling and `normalize: true` — bge-m3's documented dense-retrieval recipe. Normalizing the vectors means cosine similarity reduces to a plain dot product in SQL.
- **`getEmbedder`** — the factory callers use to obtain a provider (returns a `LocalBgeM3`), keeping the concrete class behind the interface.
- **`embeddingInput`** — builds the exact string that gets embedded for a chunk: a prepended context line (`"CGST-ACT | CHAPTER V — INPUT TAX CREDIT"`) followed by the chunk text. *Why it matters:* a chunk's body often never names its own act or chapter, so this line injects that identity into the vector — a dozen tokens that disambiguate hundreds of otherwise look-alike provisions. This must produce the same format used at ingestion time so query and chunk vectors are comparable.

### `lib/retrieval/config.ts`
A tiny but load-bearing config file that pins the embedding model. It exists because embeddings are only comparable when produced by identical model weights — if the model drifts, new query vectors and old chunk vectors live in subtly different meaning-spaces and search quality decays with no error anywhere.

- **`EMBEDDING`** (const) — the pinned embedding settings: `provider` (`local-transformers`), `modelId` (`Xenova/bge-m3` — the strongest open multilingual retriever, so it handles Hinglish against English legal text), `revision` (`main`, with a TODO to pin to a commit hash after the golden-set eval blesses it), and `dimensions` (1024, matching the `vector(1024)` Postgres column exactly). 🔒 Treated as a migration surface: the header comment states that changing anything here requires re-embedding every chunk and re-running the eval set before shipping — the discipline that keeps retrieval quality from silently rotting.

## 7 · The Gates

### `lib/gates/verify-citations.ts`
The citation gate: deterministic, model-free code that checks a generated RAG answer is actually grounded in the law chunks retrieval provided. It proves "real vs invented citation" with arithmetic (set membership), not judgment — 🔒 an invented citation cannot be argued past a `Set.has()` check because there's no prose channel to persuade.

- **`ABSTAIN_PHRASE`** — the canonical "the available sources don't cover this point" string. It's a shared constant so the gate can recognize an honest abstention and exempt it from the tag-required rule (an abstention makes no legal claim, so it needs no citation). 🔒 This is the honest-abstention escape hatch.
- **`CitationCheck`** (type) — the gate's verdict shape: `ok` (passed both checks), `cited` (all tag ids found), `invalid_tags` (cited ids retrieval never provided — invented or mangled), and `untagged_sentences` (claim-sentences missing a citation). Structured so a caller can both decide and explain *why* it failed.
- **`TAG_RE`** (const) — the regex that finds citation tags like `[CGST-ACT/s17]`. The trick: an optional trailing parenthetical (a subsection like `(5)`) is matched but excluded from the captured id, so a model citing `[CGST-ACT/s17(5)]` normalizes to the same chunk id `CGST-ACT/s17` — legal precision isn't punished as a mismatch.
- **`CLAIM_MARKERS`** (const) — a regex listing tell-tale signs of a legal assertion: a digit, `₹`, `%`, words like `section`, `shall`, `liable`, `exempt`, `penalty`, `due date`, `itc`, etc. The mechanism: only sentences that *look like* legal claims are required to carry a citation; pure navigation text ("let me explain both cases") carries none of these markers and is skipped. This keeps the gate from flagging harmless connective prose.
- **`isExempt`** — decides a sentence plainly isn't a legal claim and so needs no tag. How: a short OR-chain of cheap checks — markdown headings/table rows (`#`, `|`), very short sentences (< 25 chars or ≤ 6 words), the abstention phrase, questions (`?`), list intros (`:`), and connective openers ("in short", "however", "consult", "your options"). Anything matching is waved through untagged.
- **`verifyCitations`** — the main check; returns a `CitationCheck`. How it works in two passes: (1) it regex-extracts every cited id and flags any not in the `provided` Set as `invalid_tags` 🔒 (invented-citation catch); (2) it walks line-by-line, splitting each line into sentences (on `.`/`!` boundaries), and for every sentence that is a claim (passes `CLAIM_MARKERS`, fails `isExempt`) with no tag, records it as `untagged_sentences` 🔒 (untagged-claim catch). A subtle bit: bullet sub-items can *inherit* a citation from a tagged intro line in the same list block (`blockHasTag`), and a blank line resets the block — so legitimately-grounded bullet lists aren't falsely flagged. `ok` is true only when both lists are empty. Note it resets `TAG_RE.lastIndex = 0` after each `.test()` because the regex is stateful (global flag).
- **`pruneUngrounded`** — the gentler enforcement path; returns cleaned `text` plus `hasGroundedClaim`. Why it exists: the old all-or-nothing rule threw away the *whole* answer over one bad sentence, which suppressed nearly every RAG answer. Instead it drops *only* the offending sentences (untagged claims, or claims citing a source retrieval never provided) and keeps the properly-cited remainder, rebuilding each line from the surviving sentences. 🔒 The hard safety still holds — an ungrounded claim is never shown to the user, it's just excised surgically. It uses the same claim/exempt/bullet-inheritance rules as `verifyCitations` (so acceptance and pruning agree), and reports `hasGroundedClaim: false` when nothing survived, letting the caller abstain honestly rather than emit an empty answer.

### `lib/gates/g3-recompute.ts`
The G3 "recompute, don't trust" gate: deterministic, model-free code that verifies every number a resolution draft asserts (₹ amounts, %, day/month/year counts) actually appears in a cited chunk's text or in calculator output. 🔒 This makes a model quoting a figure "from memory" that isn't in its source mechanically impossible to pass — the failure the product brief forbids.

- **`NUM_WORDS`** (const) — a lookup map from number-words to values (`one`→1 … `crore`→10000000, including Indian units `lakh`/`crore`). Used to translate spelled-out numbers so "five lakh" and "500000" compare as equal.
- **`normalizeNumbers`** — canonicalizes a string's numeric notation so equivalent figures match regardless of how they're written. How: lowercases; converts `per cent`/`percent`→`%` and strips currency markers (`₹`, `rs.`, `rupees`); folds word-pairs like "five lakh" into `500000` via `NUM_WORDS`; maps bare number-words to digits; removes the thousands-comma (`1,00,000`→`100000`); and collapses whitespace/punctuation. The result is a normalized haystack/needle both source and draft are run through, so comparison is apples-to-apples.
- **`TAG_RE`** (const) — same citation-tag regex as the citation gate, used here to find which chunk ids a line cites so the gate knows *which* source texts to search for that line's numbers.
- **`NUMBER_RE`** (const) — the regex for numbers worth verifying: 2+ digit figures, percentages, and digit+unit pairs (e.g. `18%`, `30 days`, `2 crore`). Single digits are deliberately excluded as too noisy.
- **`G3Result`** (type) — the verdict: `ok` (no violations) and `violations` (human-readable strings naming each unverifiable figure, the sentence it's in, and which sources were searched).
- **`recomputeNumbers`** — the main gate. For each line of the draft it: (1) collects the line's cited chunk ids via `TAG_RE` and gathers those chunks' text plus all calculator outputs into one normalized "source" haystack; (2) normalizes the line itself and pulls out every candidate number via `NUMBER_RE`; (3) for each figure, checks the bare digits appear in the source haystack — if not, records a violation. 🔒 A figure not found in any cited source or calculator output fails the gate. Two deliberate false-positive guards: single digits (< 2 digits, non-percent) are skipped as too noisy, and digits glued to letters — `GSTR-1`, `3B`, section numbers — are treated as identifiers, not asserted amounts, and skipped (via a regex checking for an adjacent letter). `ok` is true only when no figure went unverified.

## 8 · Observability, Database & UI

### `lib/observability/langfuse.ts`
The single place GSTPilot talks to Langfuse (the tool that records every model call and eval as a browsable trace tree). It centralises credentials and makes all observability writes best-effort, so logging can never crash the thing it's logging.

- **`LfTrace` / `LfSpan` / `LfParent`** — type aliases for "something a child observation can hang under" (a whole-turn trace, or a span inside it). Their trick: instead of importing named SDK types, they *derive* the types from what the SDK's own methods return (`ReturnType<...>`), so they stay correct even if the library renames things. This is what lets one model call nest under whatever parent you pass, turning a flat log into a tree.
- **`recordGeneration`** — runs a model call and simultaneously records it as a "generation" node in the trace, capturing model name, input, output, and token counts (so the call is visible and cost-attributed). *How:* it opens a child node on the `parent`, runs your `fn`, then uses the caller-supplied `extract` to map the raw result into what the node should display — one generic helper reused by every model call (Haiku classifier, Sonnet answer-writer, etc.). 🔒 Best-effort by design: if no `parent` is passed it just runs `fn` (so eval/standalone paths never break), and on error it marks the node `ERROR` but still re-throws so real failures surface.
- **`getLangfuse`** — returns the Langfuse client, building it once and caching it. *How:* the `client ??=` idiom means "create only if not already created," reading the three env-var credentials in exactly one spot.
- **`langfuseHost`** — returns the configured Langfuse host URL, defaulting to the cloud instance when the env var is unset.
- **`getLangfuseProjectId`** — resolves the Langfuse project id needed to build a *clickable* trace URL (a bare `/traces/<id>` link 404s). *How:* it checks a cache, then an env override, then as a last resort calls Langfuse's public API with HTTP Basic auth (base64 of the public:secret keys) and takes the first project's id. Failure is swallowed and cached as `null` so it never throws. The `cachedProjectId !== undefined` check distinguishes "not fetched yet" from "fetched, got nothing."
- **`langfuseTraceUrl`** — builds the correct deep link to a trace. *How:* if the project id resolves it returns the full `/project/<id>/traces/<id>` URL, otherwise it degrades to the imperfect bare URL — it always returns *something*, never nothing.

### `lib/supabase.ts`
The one server-side gateway to Supabase (GSTPilot's hosted Postgres database, which also holds the law chunks). It uses the powerful service-role key, so 🔒 it must never be imported into browser code — that key bypasses all row-level security.

- **`TABLE_PREFIX`** — the exported constant `"gstpilot_"`. Because the app temporarily shares a staging database, every table name is built from this prefix rather than hard-coded; moving to a dedicated database later is a one-string change.
- **`getServiceClient`** — returns the shared Supabase client, creating it on first use and caching it (so the HTTP connection pool isn't rebuilt each request). *How:* it reads `SUPABASE_URL` and the service-role key from the environment and 🔒 throws a clear, actionable error if either is missing. It's deliberately lazy (a function, not a top-level constant) so files that load before `.env` exists don't crash at import time — the failure lands exactly where the database is actually used. The client is configured with no session persistence and no token refresh, because a server process isn't a logged-in person.

### `app/page.tsx`
The chat UI — the product's face. A React client component rendering the thread of questions and cited answers, streaming the agent's progress live and collecting thumbs feedback. Citations render as expandable cards showing the exact quoted legal text, which builds more trust than a bare link.

- **`Citation` / `Msg`** — the shape of the data the UI renders: a `Citation` is an id + heading + quoted snippet; a `Msg` is one chat bubble carrying role, text, and (for assistant replies) risk `tier`, `citations`, a `messageId`, whether it `escalated`, and any feedback given.
- **`STEP_LABELS`** — a lookup table mapping each pipeline step name (e.g. `intake`, `G4-citations`, `retrieval`) to a friendly Hinglish status line. *How:* as the server streams "I'm now at step X" events, the UI shows the matching phrase so the wait reads as the agent genuinely working through the law, not a dumb spinner. Note the step names mirror the safety gates (`G1`–`G5`) from the pipeline.
- **`EXAMPLES`** — five one-tap starter questions chosen to showcase breadth (rate lookup, e-commerce/TCS, refund, late fee, e-way bill).
- **`TIER`** — maps each risk tier to a plain-language label and colour class: calm teal for T1 (general info), amber for T2 (your money/deadline), rust for T3 (escalated to a CA). Colour carries the risk level at a glance.
- **`ChatPage`** — the default exported component; holds all state (`msgs`, `input`, `busy`, `status`) and a `threadRef` so follow-up questions stay in one conversation. An `useEffect` auto-scrolls to the newest turn whenever messages or status change.
  - **`ask`** — drives one question→answer turn. *How:* it POSTs the question to `/api/ask`, then reads the response as an **SSE stream** (Server-Sent Events — the server pushes a sequence of `data:` lines as it works). It accumulates raw bytes in a buffer, splits on the `\n\n` frame delimiter, JSON-parses each `data:` line, and reacts by event type: `thread` stores the conversation id, `status` updates the live label, `answer` appends the finished reply (with tier/citations/messageId), `error` shows a Hinglish apology. Two robustness tricks: a `try/catch` around the parse silently waits for more bytes when a frame arrives half-formed, and it keeps the trailing partial frame in the buffer via `lastIndexOf("\n\n")`. The `override` argument lets example chips submit directly, sidestepping the race where React's async `setInput` hasn't updated yet.
  - **`sendFeedback`** — sends a 👍/👎 (with an optional reason) for a message. *How:* it optimistically flips that message's `feedback` in local state first (instant UI response), then POSTs `messageId` + `verdict` + `reason` to `/api/feedback`; it early-returns if the message has no `messageId` to attach the vote to.
  - **JSX render** — lays out header, thread, and composer. User bubbles are simple; assistant bubbles carry the 🔒 tier badge, the answer text, expandable **`<details>`** citation cards (each quoting the snippet with a "Read the full section" deep link), a 🔒 "Talk to a CA" button that appears only on T2/T3 replies, and the feedback row. A bouncing-dots indicator shows the current Hinglish `status` while `busy`. The composer form calls `ask()` on submit and carries the standing 🔒 "Information, not professional advice… disputes go to a Chartered Accountant" disclaimer beneath it.
- **`EmptyState`** — the first-run welcome canvas shown when the thread is empty. Renders the example chips as clickable buttons (via the `onPick` callback) so a blank thread doubles as a demo and never feels like a dead end.

### `app/api/feedback/route.ts`
The `POST /api/ask`-sibling endpoint that records a thumbs up/down on an assistant message. It writes the verdict to the database and mirrors it as a Langfuse score, because down-voted traces are the raw material for new golden test cases in Phase 8.

- **`POST`** — the route handler. *How:* it reads `messageId`, `verdict`, and `reason` from the JSON body and 🔒 validates them first — rejecting with HTTP 400 unless `messageId` exists and `verdict` is exactly `"up"` or `"down"` (a closed-list check, so no arbitrary value gets stored). It then updates the message row in the `gstpilot_messages` table (storing the reason only for down-votes) and reads back the row's `trace_id`. If a `trace_id` exists, it attaches a Langfuse `user_feedback` score (1 for up, 0 for down, with the reason as a comment) and flushes it. 🔒 That Langfuse block is wrapped in a `try/catch` that swallows errors, upholding the project-wide rule that observability never blocks the user-facing response. On a database error it returns HTTP 500; otherwise `{ ok: true }`.
